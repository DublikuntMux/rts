# Multiplayer protocol

Shared interfaces for the authoritative server and clients.

- `rts_net` depends on base, serde, RON, thiserror, and the pure-Rust miniz_oxide codec. Messages use bounded RON text for lobby/gameplay and raw binary frames for setup, protocol version 4. No renderer or socket dependency in the protocol. Older clients/replays are incompatible.
- `MatchSetup { rules: String, map: String, seed: u64, players: u8 }` contains RON documents in their data-file units. `minified()` removes comments and unnecessary whitespace without changing literal bytes or parsed values. `checksum()` hashes the minified documents with lengths, seed, slot count and protocol version, so formatting/comments do not change readiness; `simulation()` validates the content and exact map player count.
- `ClientMessage`: `Create { version }`, `Join { version, code }`, `Ready { checksum }`, `Start`, `Input { tick, commands }`, `Leave`. Clients cannot upload rules, player identities, state or hashes.
- `ServerMessage`: `Setup(MatchSetup)`, `Lobby { code, player, players, capacity, ready }`, `Started { players, input_delay }`, `Turn { turn: Turn, hash: u64 }`, `Ended { reason }`, `Error { message }`. The turn's hash is the server state after applying that turn. On the wire, `Setup` is binary-only: a 33-byte header followed by the raw rules and map zlib streams. Header fields, in order: four-byte `RTSS` tag, `u32` protocol version, `u64` seed, `u8` player count, `u32` rules decompressed length, `u32` rules compressed length, `u32` map decompressed length, `u32` map compressed length. Multibyte values use little-endian encoding. Each document is lexically minified then compressed with zlib/DEFLATE at level 6. There is no base64 or RON wrapping around the compressed bytes. Application code receives ordinary minified `MatchSetup` strings after decoding. `encode_server` returns `ServerFrame::Binary(Vec<u8>)` for setup and `ServerFrame::Text(String)` for other messages; `decode_server_binary` and `decode_server` decode their respective frame types. Text setup and unknown binary tags/versions are rejected.
- The server loads and validates its setup before accepting connections. Each creating/joining player receives `Setup` before the lobby update, validates it and sends `Ready` with the received checksum. A client never compares this against its bundled configuration. Only slot-zero host may start a full room, and every occupied slot must acknowledge the setup first. Room capacity comes from the server map; codes are six uppercase alphanumeric characters. Pregame guest departure frees the slot and clears its readiness; host departure closes the room.
- Every room owns a server-side `Sim`. Once started, the server advances at `TICK_RATE = 20` regardless of incoming commands. The first turn occurs one tick after start. Missing submissions become empty player batches. Catch-up is bounded so a suspended runtime cannot flood clients with an unlimited burst.
- Clients submit input for their latest received server tick plus `INPUT_DELAY_TICKS = 2`. Input is authenticated by connection slot, restricted to future ticks with a maximum lead of eight, and must increase without duplicate submissions; gaps are allowed. The server enforces command/selection limits and rejects repeated IDs within a selection and excessive repeated orders for a unit in one batch. Simulation validates ownership, target terrain, path reachability, speed and capacity. No client can command another player's units or directly set health/position. Invalid simulation orders have no effect.
- `PlayerInput { player: PlayerId, commands: Vec<Command> }`; `Turn { tick: u32, inputs: Vec<PlayerInput> }`. Each server turn has exactly one ascending batch per player; commands retain submission order. `Turn::apply` checks sequential tick and advances once without adding another delay.
- Clients apply only server-issued turns and verify each resulting hash before recording. Clients drain up to eight buffered turns per fixed update to catch up after slow rendering. Missing turns pause the local replica and retain pending input; a 15-second lack of progress or a hash mismatch stops that client. Client hash reports are absent, so client consensus cannot override the server or control its clock. A real disconnect or socket timeout ends the room for its remaining players. Socket/lobby timeouts and bounded queues remain enforced by the runtime.
- This is deterministic command replication with server authority. It does not yet send corrective snapshots, support reconnect/late join, or filter hidden state. A modified client can alter its own display, but cannot change the server simulation. Fog-of-war confidentiality needs a later visibility-aware protocol.
- Client input messages are limited to `MAX_MESSAGE_BYTES = 65536`, 64 commands per player per turn, 1024 selected unit occurrences per batch (at most 1024 per command), no duplicate IDs within a command, and at most four orders per unit per batch. Aggregated server turns have a separate bounded allowance for all eight players. Binary setup messages allow up to `MAX_SERVER_MESSAGE_BYTES = 16 MiB + 33 bytes`. Each original/minified RON document is limited to 4 MiB and each compressed stream to 8 MiB. Both documents' declared sizes and the complete payload framing are checked before decompression. The declared decompressed length is checked before allocation; inflate must produce exactly that length, validate the zlib checksum and consume the entire stream. Truncation, trailing data, corrupt streams, invalid UTF-8 and excess expansion are rejected before setup acknowledgment. Other server messages retain the 64 KiB limit. Text wire/replay nesting is bounded to 64 levels; embedded map/rules parsers use a 128-level bound.
- Replay `Replay { version, setup, turns, final_hash }` embeds the received minified server setup and every applied turn. Replay files retain plain RON setup strings for inspection rather than the transport compression envelope; offline recordings may retain their original formatting. `Replay::new`, `push`, `to_ron`, `from_ron` and `playback` validate setup, continuity, command limits and final state. Replays are limited to 32 MiB and one million turns. Solo play and playback use the same deterministic simulation without a socket.
- ewebsock clients support native `ws://` and browser `ws://`/`wss://`. The Tokio/tokio-tungstenite server accepts plain WebSockets; use a TLS reverse proxy for HTTPS browser hosting. Native TLS is disabled because standard Rustls providers introduce C/assembly dependencies.
- The socket runtime is native-only with a wasm build stub. The deterministic protocol and coordinator build across native, wasm and Android. Dependencies remain centralized in workspace configuration.
- The seed is included in setup/checksum/replays but remains reserved until simulation randomness is implemented. Configuration delivery covers all currently implemented rules and map data. Texture images remain local presentation assets; use bundled texture paths or terrain colors for server-only content mods.
